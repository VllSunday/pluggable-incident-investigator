# Архитектурный аудит по книге «Глубокое понимание AI Agent»

Источник: Ли Боцзе, неофициальный русский перевод, версия 2026-8. Анализ относится к локальному
PDF `AI-Agents-in-Depth-ru.pdf` и сопоставляет рекомендации книги с текущим проектом.

## Главный вывод

Проект движется в правильном направлении не потому, что в нём несколько названных ролей, а
потому, что большая часть ценности находится в Harness вокруг модели. В терминах главы 1 система
уже реализует пять ключевых функций: context, tools, constrain, verify и correct. Policy engine,
durable checkpoints, sandbox, approval и recovery verifier важнее ещё одного промпта «агента».

Книга также даёт полезный критерий мультиагентности (глава 10): дополнительная роль приносит
ценность, только если получает новую информацию. Поэтому проекту не нужен декоративный
«совет агентов», обсуждающих один текст. Сильный контур здесь — investigator → реальный tool
result → critic. Тесты, метрики и recovery checks добавляют информацию, которой не было в
первоначальном ответе модели.

## Что уже соответствует рекомендациям

| Рекомендация книги | Реализация в проекте |
|---|---|
| Смешивать детерминированный workflow и автономные решения | Явный LangGraph, внутри которого LLM выбирает гипотезы и предложение действия |
| Разделять восприятие и исполнение | Read-only evidence providers отделены от action executors |
| Ограничивать, проверять и исправлять | Policy, typed schemas, retry, Reflexion, sandbox и recovery verification |
| Делать события асинхронными | Webhook быстро отвечает `202`, durable worker продолжает thread в фоне |
| Ставить человека на рискованных границах | Approval перед runtime action и публикацией PR/MR |
| Возобновлять прерванную задачу | `awaiting_input` продолжает тот же LangGraph checkpoint |
| Использовать внешнюю обратную связь | pytest/Ruff, Prometheus, health endpoint и critic |
| Оценивать не только финальный текст | Ground-truth eval учитывает evidence, terminal state, budget и safe action |

## Улучшения с наибольшей отдачей

### P0 — до production-пилота

1. **Pass^k вместо одиночного demo.** Глава 6 подчёркивает, что бизнесу важна серия
   последовательных успехов. Eval runner должен запускать каждый CI/runtime case 5–10 раз и
   отдельно считать success, unsafe action veto, tool errors и стоимость.
2. **Атрибуция места отказа.** Классифицировать failure как observation, reasoning, action,
   verification или environment. Сейчас trace есть, но итоговый eval недостаточно точно говорит,
   на каком участке сломалась траектория.
3. **Budget-aware стратегия.** Одного жёсткого лимита мало. В начале расследования агент должен
   исследовать несколько независимых источников, а при малом остатке бюджета — проверять ведущую
   гипотезу либо формулировать точный запрос человеку.
4. **Read-only production provider логов.** Добавить Loki или Elasticsearch adapter. Без логов
   runtime-контур остаётся демонстрационным, хотя Prometheus adapter уже пригоден для реальной среды.

### P1 — после первых реальных трассировок

5. **Vendor-neutral telemetry.** В дополнение к LangSmith экспортировать spans в OpenTelemetry /
   OpenInference: LLM call, tool call, retries, tokens, latency и error class.
6. **Прогрессивное раскрытие инструментов.** При росте числа адаптеров не передавать модели весь
   каталог. Выбирать небольшой набор tools/capabilities по source, incident kind и текущему этапу.
7. **Incident knowledge retrieval.** Хранить проверенные runbooks и похожие закрытые инциденты,
   извлекать их по требованию с provenance. Непроверенные логи не должны автоматически становиться
   инструкциями.
8. **Сохранять отрицательные результаты.** Записывать отвергнутые гипотезы, провалившиеся
   проверки и причины остановки, чтобы агент не повторял уже опровергнутый путь.

### P2 — контролируемая эволюция

9. **Production trace → regression case.** После redaction подтверждённый bad case превращается
   в новый eval fixture. Это замыкает observability и evaluation.
10. **Кандидатные runbook updates через PR.** Агент может предложить обновление инструкции, но
    не должен сам изменять policy, eval cases, safety thresholds или audit log. Книга прямо отделяет
    кандидатные способности от официальных.
11. **Ablation switches.** Сравнивать полный graph, graph без Reflexion и single-pass baseline на
    одинаковых case/seed/budget. Так можно доказать вклад архитектуры, а не только модели.

## Что не стоит добавлять

- Несколько одинаковых LLM-ролей для голосования без новых evidence.
- Неограниченный shell ради «универсальности».
- Автоматическое обучение на сырых логах и ответах инструментов.
- Автоматический merge или изменение safety policy самим агентом.
- Бесконечное увеличение tool/iteration budget в надежде на лучший результат.

## Рекомендуемый порядок

Сначала Loki provider, Pass^k runner и failure attribution. Затем провести shadow-пилот и
собрать обезличенные bad cases. Только после измерений решать, нужны ли дополнительные
специализированные агенты или достаточно текущего workflow с внешней обратной связью.
